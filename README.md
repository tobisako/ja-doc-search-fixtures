# ja-doc-search-fixtures

**日本語の書類が「抽出できたのに検索できない」状態を再現する、20本のテストデータ。**

自分の抽出処理をこれに通すと、日本語の取りこぼしが出ます。

```bash
./check.py --cmd "python3 my_extract.py {file}"
```

**図でわかる解説 → https://tobisako.github.io/ja-doc-search-fixtures/**

---

## こんな人に使ってほしい

> **日本語の社内文書を検索できるようにしたら、「あるはずの契約書が出てこない」と言われた人。**
> 原因を突き止めて直したあと、**それが二度と起きないことを、これから先も確かめ続けたい人。**

一度直して終わりなら、これは要りません。`NFKC` を1行足せば済みます。

要るのは、**直したあとも壊れないことを検証し続ける必要がある人**です。
ライブラリを更新したとき、PDF生成元が変わったとき、別の部署のファイルが入ってきたとき。
そのたびに「失敗するPDFを何種類も自分で作る」のは現実的ではありません。

**この20本がその材料です。**

具体的には、こういう場面です。

- 社内文書の**全文検索**を作っていて、日本語PDFが対象に入っている
- **RAG** を作っていて、検索結果に**原文の該当箇所**も出している（位置がずれると困る）
- 抽出ライブラリ（`pypdf` / `pdfplumber` / `pdf-parse` / `unpdf` など）を**更新する予定がある**
- 契約書・請求書を扱っていて、**全角と半角の違いが意味を持つ**

## こういう人には要りません

- 英語の文書だけを扱っている
- 一度直せば十分で、再発を検証する必要がない
- 表構造やレイアウトが目的（それは [Docling](https://github.com/docling-project/docling) の領域です）

---

## なぜ要るのか — 実測

日本語のPDFに「人事評価制度の見直し」と書いてある。画面では普通に読める。
`pypdf` と `pdfplumber` で抽出すると **53文字ちゃんと返る。例外も警告も出ない。**

```python
text = extract(pdf)     # '⼈事評価制度の⾒直しについて…'   53文字
'人事' in text          # False   ← 検索できない
```

```
実際   : U+2F08 U+4E8B（⼈事）   ← U+2F08 は「康熙部首」の人
正しい : U+4EBA U+4E8B（人事）
```

**エラーは出ない。目で見れば読める。検索だけが 0 件になる。**
RAG に入れると「該当なし」が返り続け、原因がPDFの文字コードだと辿れる人はほぼいません。

もうひとつ。**テキスト層のないPDF（スキャン）は、`pypdf` も `pdfplumber` も空文字を返します。
例外なし・警告なし。** 空のままインデックスされ、失敗したことすら分かりません。

## `NFKC` では直しすぎる

`text.normalize('NFKC')` を掛ければ康熙部首は直ります。**が、全角も潰します。**

```
（消費税別） → (消費税別)
１２３４５６７ → 1234567
ＡＢ－１２０  → AB-120
```

契約書・請求書では、これで原文と一致しなくなります。
**検索結果に原文の該当箇所を出しているなら、位置がずれます。**

だからこの fixtures は、
**「⼈事 は直す」と「（消費税別） は残す」を同時に検査します。**
片方だけ通っても合格になりません。

## 使い方

抽出コマンドを1つ用意してください。**ファイルパスを受け取り、抽出結果を標準出力に出す**だけです。

```python
# my_extract.py
import sys, pypdf
r = pypdf.PdfReader(sys.argv[1])
text = ''.join(p.extract_text() or '' for p in r.pages)
if not text.strip():
    sys.exit(1)      # 読めないときは終了コード1。空文字を出さない
print(text)
```

```bash
./check.py --cmd "python3 my_extract.py {file}"
```

```
✗ [kangxi] K01_康熙部首_人_U+2F08.pdf
      「人事」が見つからない（NFKC を掛ければ見つかる＝正規化されていない）
      U+2F08 「⼈」がそのまま残っている（正規化されていない）
      → 「人」が U+2F08（康熙部首）。53文字返るが「人事」で検索できない
✗ [no-text] N01_スキャン_テキスト層なし.pdf
      抽出できないはずが、成功して 0文字返った（空文字を成功として返している）
      → スキャン原稿。pypdf も pdfplumber も空文字を返す（例外なし・警告なし）

合格 6 / 不合格 14（全 20本）

落ちた分類:
  kangxi     4本
  encoding   4本
  zenkaku    2本
  dakuten    2本
  compat     1本
  no-text    1本
```

これは `pypdf` の**実測結果**です（この20本を実際に通したもの）。

分類ごとに絞れます。

```bash
./check.py --cmd "..." --group kangxi
```

**`check.py` は標準ライブラリだけで動きます。このファイルごと自分のCIにコピーして構いません。**
依存を増やす必要はありません。

## この20本は、実際に起きることをそのまま収めたもの

検査用のテストデータですが、**細工はしていません。
Chrome で日本語のHTMLをPDFに書き出すだけで、康熙部首が混ざります。**

```
文 → ⽂ (U+2F42)     身 → ⾝     口 → ⼝ (U+2F1D)
行 → ⾏ (U+2F8F)     見 → ⾒     支 → ⽀ (U+2F40)
```

作った本人が意図した文字ではありません。**フォントとレンダラがそうします。**
だから実務のPDFにも普通に入っています。

この事情があるので、`expected.json` の `must_not_contain_cp` は
**実ファイルの中身から機械的に導いています**（`tools/derive.py`）。
手で書くと実物と食い違います（実際に食い違わせました）。

## NFKC でも直らないものがある

CJK部首補助のうち **U+2E8C（⺌）や U+2E85（⺅）には NFKC の対応表がありません。**
どのツールでも直せません。これらは `known_unfixable_cp` として記録し、
**判定には使いません**（誰にも通せない試験にしないため）。

## 2つの入口 — CLI と Web API

**CLI が主です。** 抽出ツールを自分で実行して、手元や CI で繰り返し検証します。

```bash
./check.py --cmd "python3 my_extract.py {file}"
```

**Web API は、抽出した結果を送って採点してもらう入口です。** こちらは抽出を実行しません。
ブラウザから貼って試したいとき、既存の Web ツールから HTTP で採点したいときに使います。

```bash
cd server && npm install && npm run build && node dist/main.js
```

| | 何をする | 抽出を実行するか |
|---|---|---|
| **CLI** `check.py` | 抽出コマンドを走らせて採点 | **する** |
| **Web API** `server/` | 送られた抽出結果を採点 | **しない** |

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/fixtures` | 20本の一覧と、それぞれ何を証明するか |
| `GET` | `/fixtures/:file/raw` | テストデータの実体 |
| `POST` | `/check` | 1件を採点 |
| `POST` | `/check/batch` | まとめて採点。合計と分類ごとの内訳 |

```bash
curl -X POST localhost:3100/check \
  -H 'content-type: application/json' \
  -d '{"file":"K01_康熙部首_人_U+2F08.pdf","text":"⼈事評価制度の⾒直しについて"}'
```

**抽出できなかったときは `{"file":"...","failed":true}` を送ります。**
空文字を送ると「0文字で成功した」と採点されます。`text` と `failed` の同時指定は断ります
（抽出できたのかできなかったのかが決まらないため）。

**`failed` は送り手の申告です。このサーバが抽出を試したわけではありません。**
その旨は応答にも入っています。

### 2つの採点結果は一致します

同じ `expected.json` と同じ判定ロジックを使います。実測で確認しています。

```
WEB : 合格 6 / 不合格 14 / 未実施 0
CLI : 合格 6 / 不合格 14
一致: ✅（落ちたファイルの集合も同一）
```

**まとめて採点したとき、送らなかったものは `notSubmitted` として名前が返ります。**
黙って母数から外しません。3本だけ送って「20本中3本合格」に見えることを防ぐためです。

### 実装

Web API は **NestJS**（TypeScript）で書いています。CLI は Python の標準ライブラリだけです。
採点そのもの（`CheckService`）は HTTP を知りません。CLI と同じ4種類の判定を、同じ基準ファイルで行います。

## 収録しているもの（20本）

| 分類 | 本数 | 何を検査するか |
|---|---|---|
| `kangxi` | 4 | 康熙部首・CJK部首補助。**見た目は正しく、検索だけ0件になる** |
| `compat` | 1 | CJK互換漢字 U+FA19（人名で出る）。**PDFでは消えるのでテキストで置いた** |
| `zenkaku` | 3 | **NFKC で潰してはいけないもの**（全角括弧・全角数字・全角英字） |
| `dakuten` | 2 | 半角カナの濁点・半濁点。**分解形のままだと合成済みの文字で一致しない** |
| `no-text` | 3 | テキスト層なし。**空文字で成功にしてはいけない** |
| `broken` | 3 | 0バイト・拡張子詐称・途中で切れたPDF |
| `encoding` | 4 | CP932 / EUC-JP / UTF-16 / ISO-2022-JP |

各ファイルが何を証明するかは [`expected.json`](expected.json) に書いてあります。

### 判定の意味

| キー | 意味 |
|---|---|
| `must_find` | 抽出結果に含まれているべき語 |
| `must_keep` | **潰してはいけない**文字列（NFKC を掛けると壊れる） |
| `must_not_contain_cp` | 残っていてはいけないコードポイント |
| `must_fail` | **抽出は失敗すべき**（空文字を返してはいけない） |

## 中身について

すべて**このリポジトリで生成した架空の文書**です。実在の個人・団体とは関係ありません。
再生成は `python3 tools/make.py`（macOS + Chrome + Poppler が要ります）。

## 参考実装

上の検査を全部通す実装が必要なら、[jp-doc-extract](https://github.com/tobisako/jp-doc-extract)
（TypeScript / MIT）があります。**ただし依存に加える必要はありません。**
`NFKC` ではなく「康熙部首・互換漢字・半角カナだけを直し、最後に NFC で合成する」
という方針だけ持ち帰れば、自分の言語で書けます。

01

一番やっかいなのは、
エラーが出ないこと。

コンピューターは、文字を番号で区別します。この番号の決め方が Unicode（ユニコード）です。U+4EBA は「4EBA番の文字」という意味です。

ふつうの「人」は U+4EBA。そっくりな「⼈」は U+2F08。後者は康熙部首（こうきぶしゅ）という、漢字の部品を表す文字の一つです。番号をそのまま比べる検索では、別の文字として扱われます。

53

文字は、ちゃんと返ってくる。
例外も警告も出ない。

このテストの「人事」と書いてあるPDFから、pypdf（PythonでPDFを読む道具）で文字を取り出すと、53文字ちゃんと返る。例外も警告も出ない。それでも、「人」の中身は U+2F08 です。

実測した抽出結果を、Pythonで検索すると
# text はPDFから取り出した文字列
len(text)        # 53
"人事" in text   # False
# False =「含まれていない」

「例外」は処理を止める異常、「警告」は注意のお知らせです。この例では、どちらも出ません。

気づくのは、「あるはずの書類が出てこない」と言われたとき。そのとき、原因をPDFの文字の番号まで辿れる人はほぼいません。見た目は読めて、処理も成功しているからです。
02

書いた人は、何も間違えていない。

このリポジトリの生成環境では、Chromeで日本語HTMLをPDFにするだけで、別番号の文字が混ざります。HTMLは、Webページを書くための形式です。

細工ではない。フォントとレンダラがそうする。フォントは「文字の形のセット」、レンダラは「文字や図を画面やPDFに描く仕組み」です。その組み合わせによって、PDFから取り出す文字の番号が変わることがあります。

つまり、「書いた人が変な文字を入力した」とは限りません。PDFにする途中で、意図しない文字になっているのです。

すべての環境で起こるわけではありません。使うフォント、変換方法、ソフトの版によって結果が違います。実際の調査と大学のFAQでも、この違いが報告されています。
03

まとめて直すと、直しすぎる。

NFKC は、文字の形や種類の違いをまとめてそろえるルールです。「⼈」を「人」にできます。でも、残してほしい全角の括弧や数字まで、半角に変えてしまいます。

契約書や請求書では、原文の表記をそのまま残したい場面があります。このテストは、「⼈事」は「人事」に直すことと、「（消費税別）」はそのまま残すことを、両方確かめます。

正しい直し方は、
そっくりさんの文字だけを直すこと。

このテストでの方針です。参考実装は、康熙部首・互換漢字・半角カナを対象に直し、最後にNFC（分かれた文字と濁点などをまとめるルール）を使います。

NFKCにも、対応表がない文字があります。

U+2E8C（⺌）、U+2E85（⺅） は NFKCでも直らない文字です。NFKCの対応表だけでは、誰にも直せません。このテストでは、対応表がない文字を合否の判定に使いません。

04

直す範囲は自分で決め、
直し方はUnicodeに任せる。

テストデータの「20本」は、ファイルの本数です。直せる文字の数ではありません。直す仕組みのほうは、康熙部首214文字すべてに対応しています。

「そっくりな文字」を1つずつ手で書き並べているわけではありません。Unicode が公式に持っている変換表（NFKC）を、範囲を限定して使います。どこを直すかだけを自分で決め、何に直すかは Unicode に任せます。

全角の括弧（U+FF08）も全角の数字（U+FF10〜U+FF19）も、この5つの範囲の外です。だから変わりません。半角カタカナ（U+FF61〜U+FF9F）だけが範囲に入っています。

実際のコードは、これだけです。「この番号の範囲なら直す」と書いてあるだけで、どの文字が何になるかは1つも書いていません。

const cp = ch.codePointAt(0);
const broken =
  (cp >= 0x2e80 && cp <= 0x2eff) ||  // CJK部首補助
  (cp >= 0x2f00 && cp <= 0x2fdf) ||  // 康熙部首
  (cp >= 0xf900 && cp <= 0xfaff) ||  // CJK互換漢字
  (cp >= 0xfe30 && cp <= 0xfe4f) ||  // CJK互換形
  (cp >= 0xff61 && cp <= 0xff9f);    // 半角カタカナ

return broken ? ch.normalize('NFKC') : ch;

対象は 896文字。そのうち 769文字が直ります。

Python 3.14 の unicodedata で数えた実測値です。康熙部首は214文字すべて、半角カタカナは63文字すべてが直ります。参考実装に214文字と63文字を1つずつ通して、全部変換できることを確認しています。20本のテストデータは抜き取り検査であって、対応表そのものではありません。

直らない127文字のうち113文字は CJK部首補助です（U+2E8C（⺌）など）。Unicode に対応表がないため、NFKC では誰も直せません。このテストでは known_unfixable_cp として記録し、合否の判定に使いません。

05

このツールは、抽出プログラムの採点係。

「抽出」は、書類から文字を取り出すこと。自分の抽出プログラムに20本のテストデータを読ませ、必要な言葉が見つかるか、残すべき文字が変わっていないかを採点します。

学校のテストにたとえると

学校ではこのツールでは
問題用紙20本のテストデータ
答案自分のプログラムが取り出した文字
採点基準expected.json に書いた「あるべき結果」
点数合格数・不合格数と、終了コード

採点するのは、この4つ

  • 見つかる？ 「人事」など、必要な言葉がある。
  • 残せている？ 全角の括弧や数字が変わっていない。
  • 直せている？ 指定した別番号の文字が残っていない。
  • 読めないと言える？ 読めない書類を、空の文字列で成功にしない。
「読めません」と言えたら合格、という問題も。文字の情報がないスキャンPDFなどでは、空っぽの結果を成功として返すと見落としになります。「失敗すべき」と決めたテストでは、失敗を知らせることが正解です。

20本を実際に通すと、こうなりました。

「文字が返る」だけでは、
合格になりません。

これは、この20本での実測結果です。PDF以外の文字の保存形式や、読めない書類の扱いも採点に含みます。

すべてのPDFで同じ割合になる、という意味ではありません。20本すべてに合格しても、あらゆる書類の検索を保証するものではありません。

参考実装は jp-doc-extract。そのまま使うほか、文字の直し方を参考にして、自分のプログラムに取り入れることもできます。

07

自分の抽出プログラムで試す。

ファイルを読み、文字を返すコマンドを用意します。

my_extract.py は、自分で用意する抽出プログラムの名前です。ファイルの場所を受け取り、抽出した文字を標準出力（プログラムが文字を返す通常の出口）に出してください。読めないときは、終了コード1で終えます。

リポジトリのフォルダーで実行するコマンド
./check.py --cmd "python3 my_extract.py {file}"

{file} は、このまま書きます。check.py が、20本それぞれのファイルの場所に置き換えて実行します。採点係の check.py はPythonの標準機能だけで動きます。抽出プログラムに必要な道具は、別に用意します。

1標準出力のテキスト

各テストの合否と、問題があった理由、最後に合計を表示します。
合格 6 / 不合格 14（全 20本）

2終了コード 0 / 1

終了コードは、結果を次のプログラムに伝える数字です。
0：すべて合格。1：不合格あり。

採点結果の出力は、この2つだけ。ファイルは作りません。

直したあとも、同じテストで確かめられます。抽出に使う道具を更新したときなどに、もう一度実行できます。CI（プログラムの変更時に、自動で検査する仕組み）に組み込む使い方も考えられます。ただし、このテストをCIで使って再発を止めている人の報告は、現時点で見つかっていません。実際にどれだけ役立っているかは、まだ分かっていません。
